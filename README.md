# arc-cua

**LLM-agnostic, low-latency execution runtime for desktop computer-use agents.**

A planner/agent reasons at a high level, supplies a small concrete subtask plus the literal values and verification criteria, and `arc-cua` uses JEV for the rapid UI action loop. The planner is deliberately outside the package.

```text
any planner / CUA
      |
      | Subtask(goal, inputs, verification, constraints)
      v
+------------------+
|   arc-cua    |
|                  |
| observe desktop  |
|       v          |
| build legal      |
| action space     |
|       v          |
| JEV decision     |<----+
|       v          |     |
| freshness guard  |     |
|       v          |     |
| execute UI       |-----+
+--------+---------+
         |
         v
SUBTASK_COMPLETE / BLOCKED / NEEDS_AGENT
         |
         v
     planner
```

## Core rule

The **agent owns intent**. The executor does not invent text, numeric values, filenames, constraints, or verification criteria.

```python
Subtask(
    goal="Apply Gaussian Blur to the selected clip",
    inputs={"effect_name": "Gaussian Blur"},
    verification=("The selected clip has Gaussian Blur applied",),
    constraints=("Do not modify any other clip",),
)
```

JEV chooses things like:

```text
CLICK -> Effects button
TYPE_TEXT -> Search Effects -> input.effect_name
DOUBLE_CLICK -> Gaussian Blur
SUBTASK_COMPLETE
```

`SUBTASK_COMPLETE` means only that the **agent-supplied** criteria appear satisfied from the available structured state. The caller still owns the overall task and may perform stronger visual/semantic verification.

## Why

Normal computer-use agents often pay for a large multimodal reasoning call for almost every UI action. The intended split here is:

- **Planner / LLM:** understand intent, choose a chunked subtask, provide text/values, define success and constraints.
- **JEV:** repeatedly choose the next legal UI operation and observed target.
- **Desktop backend:** observe and physically execute native UI actions.
- **Caller:** decide the next subtask and overall completion.

The optimization target is fewer expensive reasoning calls per completed task, not fewer clicks.

## Agent-facing contract

The stable boundary is plain JSON/Python data:

```json
{
  "goal": "Open Effects and search for Gaussian Blur",
  "verification": [
    "The Effects search field contains Gaussian Blur"
  ],
  "inputs": {
    "effect_name": "Gaussian Blur"
  },
  "constraints": [
    "Do not modify another clip"
  ],
  "max_actions": 15
}
```

Any GPT, Claude, Gemini, local model, deterministic planner, or other CUA can generate that payload.

```python
from arc_cua import execute_payload

result = execute_payload(executor, payload)
```

Typical result:

```json
{
  "status": "SUBTASK_COMPLETE",
  "actions_taken": 4,
  "reason": null,
  "history": [],
  "final_snapshot": {}
}
```

## Desktop snapshot

Backends normalize whatever the OS/application exposes into a small semantic tree:

```python
DesktopElement(
    id="ax_91da...",
    role="TextField",
    name="Search Effects",
    value="",
    actions=(ActionKind.CLICK, ActionKind.TYPE_TEXT),
    source="macos_ax",
)
```

A `DesktopSnapshot` includes the frontmost app/window, semantic elements, context, and a revision fingerprint.

The policy may only select ids and operations present in that snapshot. It cannot generate arbitrary selectors or coordinates.

## Dynamic JEV action space

`TypeSafeJevPolicy`: one request asks for the operation plus speculative operation-specific heads in parallel.

Depending on the current snapshot it can create questions such as:

```text
operation:
  CLICK | TYPE_TEXT | SET_VALUE | PRESS_KEY | HOTKEY | SCROLL |
  WAIT | SUBTASK_COMPLETE | BLOCKED | NEEDS_AGENT

click_target:
  element_4 | element_7 | element_12

type_text_target:
  element_7

type_text_input:
  effect_name | filename
```

Only the head corresponding to the selected operation is consumed.

Arbitrary text is never generated by JEV. `TYPE_TEXT` and `SET_VALUE` must select one of the values supplied in `Subtask.inputs`.

## Freshness / double-action protection

Every semantic target has a guard. Before executing a chosen mutation, the backend checks that the target still means what it meant when observed.

The runtime consumes the decision before mutation and never automatically replays a successful action. If state changes before execution it re-observes and asks JEV again.

Three consecutive actions with no observable state change terminate as `BLOCKED` by default.

## Terminal states

- `SUBTASK_COMPLETE` — supplied verification criteria appear locally satisfied.
- `BLOCKED` — supported UI operations cannot make progress.
- `NEEDS_AGENT` — higher-level reasoning/perception is required, the action budget was reached, or state is too unstable.

## Install

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
```

For live JEV:

```bash
export TYPESAFE_API_KEY=...
python examples/typesafe_demo.py
```

The live JEV integration uses the SystemOne endpoint and `jev-latest` by default. Override with `TYPESAFE_MODEL` if needed.

## Run the deterministic architecture demo

No API key required:

```bash
python examples/effects_demo.py
```

It simulates a video editor and executes:

```text
CLICK Effects
TYPE_TEXT Search Effects <- "Gaussian Blur"
DOUBLE_CLICK Gaussian Blur
SUBTASK_COMPLETE
```

## macOS Accessibility backend (alpha)

This repo also includes a real semantic macOS backend based on AXUIElement. It does **not** use Blender/Adobe/etc. scripting APIs.

```bash
pip install -e '.[macos]'
python examples/macos_ax_probe.py
```

Grant Accessibility access to the terminal/Python host in **System Settings -> Privacy & Security -> Accessibility**.

Current AX backend capabilities:

- inspect the frontmost app/window accessibility tree
- normalize buttons, menus, text fields, sliders, values and state
- `CLICK` via `AXPress` / `AXShowMenu`
- `TYPE_TEXT` / `SET_VALUE` via settable `AXValue`
- safe `PRESS_KEY`, `HOTKEY`, and `SCROLL` through Quartz events
- target freshness checks before mutation

### What it intentionally does not solve yet

Professional apps contain custom canvases that may expose little useful accessibility structure: video timelines, CAD viewports, Blender node editors, bezier handles, etc. The next layer is a **pluggable visual/app-specific perception source** that emits additional `DesktopElement`s into the same snapshot. JEV should still reason over semantic ids; pixels/coordinates remain an implementation detail of the backend.

## Package layout

```text
src/arc_cua/
  api.py                 # LLM-agnostic JSON/Python boundary
  models.py              # Subtask, snapshot, action/result schemas
  protocols.py           # backend + decision policy interfaces
  validation.py          # constrain model output to observed state/agent inputs
  runtime.py             # bounded fast execution loop
  policies/
    typesafe.py           # live JEV dynamic choice policy
    scripted.py           # deterministic test/demo policy
  backends/
    memory.py             # state-machine test backend
    macos_ax.py           # real macOS accessibility backend (alpha)
```
